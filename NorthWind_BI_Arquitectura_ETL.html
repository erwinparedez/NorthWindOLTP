1. Resumen Ejecutivo y Objetivos del Proyecto

El objetivo primordial de este desarrollo consistió en transformar la base de datos relacional transaccional clásica NorthWind (OLTP) en una solución corporativa de Business Intelligence de alto rendimiento. Siguiendo rigurosamente la arquitectura de referencia de BikeStores BI, se diseñó un modelo dimensional estrella robusto, desacoplado de las tablas transaccionales, junto a un proceso ETL incremental modular mediante SQL Server Integration Services (SSIS).

Se implementó un ciclo de captura de cambios (CDC) sin triggers ni impacto transaccional, garantizando sincronizaciones periódicas en milisegundos, preservación de claves históricas, tratamiento de valores nulos o desconocidos, y orquestación visual e industrializable mediante paquetes SSIS y trabajos del Agente de SQL Server.

3. La Base Transaccional: OLTP (NorthWind)

En la base operativa se llevaron a cabo adaptaciones estratégicas para permitir una extracción no invasiva:

  • Captura de Cambios por RowVersion: Todas las tablas del modelo transaccional cuentan con una columna nativa [rowversion] [timestamp] NOT NULL. SQL Server incrementa automáticamente este contador binario ante cualquier operación de inserción o actualización, evitando el uso de triggers lentos.
  • Procedimientos de Extracción Acotados: Se parametrizaron mediante @startRow y @endRow. El procedimiento GetDatabaseRowVersion consulta MIN_ACTIVE_ROWVERSION() - 1 para fijar el límite superior activo, garantizando lecturas consistentes sin lecturas sucias.
  • Generación de Claves Sustitutas de Fecha Inteligentes: En GetSalesChangesByRowVersion, las fechas OrderDate, RequiredDate y ShippedDate se convierten directamente a enteros en formato YYYYMMDD (ej. 19960704). Los pedidos pendientes de despacho (con fecha nula) se asignan automáticamente al miembro desconocido DateSK = 0.
  • Limpieza y Reinicio de Identidades: El script clean.data.sql garantiza el reseteo de claves autoincrementales (DBCC CHECKIDENT) para garantizar pruebas reproducibles.

4. El Data Warehouse: NorthWindDW y Justificación de Diseño

Figura 2. Esquema en Estrella puro centrado en FactSales con dimensiones conformadas.

Fundamentos de Diseño Dimensional (¿Por qué se hizo así?)

1. Granularidad Atómica (Línea de Ítem de Pedido)

La tabla de hechos FactSales se definió al nivel más granular: un registro por cada producto incluido en un pedido (clave primaria compuesta OrderID, ProductSK). Esto permite calcular con total exactitud márgenes unitarios, descuentos reales e imputación proporcional del costo de transporte (FreightAllocated = Freight / LíneasDeLaOrden).

2. Desnormalización Dimensional Estratégica

En lugar de reproducir el esquema copo de nieve del OLTP (donde Productos se relaciona con Categorías y Proveedores en tablas separadas), en el DW se colapsaron en una única dimensión plana: DimProduct. Esto elimina la necesidad de realizar 3 uniones relacionales en cada consulta de análisis, maximizando la velocidad del motor analítico.

3. Dimensión de Despacho Independiente (DimDeliveryLocation)

La dirección de entrega del pedido no siempre coincide con la sede fiscal del cliente. Modelar una dimensión de ubicación geográfica de entrega independiente permite analizar la eficiencia logística, tiempos de flete y concentración regional de envíos sin distorsionar el perfil del cliente.

4. Claves Sustitutas Enteras y Miembros Desconocidos (SK = 0)

Se reemplazaron las claves naturales (como CustomerID tipo NCHAR(5)) por enteros autoincrementales de 4 bytes (CustomerSK). Esto optimiza drásticamente los índices de unión. Además, cada dimensión cuenta con un registro pre-sembrado con SK = 0 (Desconocido), lo que garantiza que nunca se descarte una transacción por falta de algún dato en origen (ej. pedidos no enviados que apuntan a ShippedDateSK = 0).

Orquestación Maestra: Package.dtsx

El paquete Package.dtsx coordina la ejecución en dos contenedores de secuencia estrictamente ligados mediante una restricción de precedencia:

  1. Contenedor de Secuencia (Dimensiones): Carga paralelizable de Clientes, Productos, Empleados, Transportistas y Ubicaciones.
  2. Contenedor de Secuencia (Hechos): Se ejecuta únicamente tras el éxito total del contenedor previo, garantizando que todas las claves dimensionales ya residan en el DW antes de cargar las ventas.
Resolución de Problema Técnico Crítico de Controladores:
Durante la fase de verificación, se detectó que los paquetes heredaban la cadena de conexión Provider=SQLNCLI11.1. Al tratarse de un controlador obsoleto no registrado en instalaciones modernas de Windows/SQL Server 2022, la ejecución fallaba con el error "Clase no registrada (0x80040154)". Se migró la totalidad de los paquetes al proveedor nativo universal SQLOLEDB, alcanzando una tasa de éxito del 100% en ejecuciones directas y por consola (dtexec).

7. Organización de Ramas en el Repositorio Git

Rama main (Data Warehouse y OLTP)

Contiene el modelo relacional, las tablas dimensionales, los scripts de post-despliegue (DWSeed.data.sql), los procedimientos de sincronización T-SQL y el script de creación del trabajo del Agente SQL (NorthWindJob.sql). No contiene la carpeta de SSIS para mantener el repositorio limpio y enfocado en la base de datos.

Rama etl (Proyecto SSIS Integration Services)

Rama derivada de main que incluye la carpeta completa NorthWindETL2/ con los 7 paquetes .dtsx, el proyecto .dtproj y la solución NorthWind.slnx enlazando los proyectos de Base de Datos y de Integración.
